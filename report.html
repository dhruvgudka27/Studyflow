Technical Report

1. RSC vs. Client Component Render Trees

StudyFlow utilizes the Next.js App Router architecture with React Server Components (RSC) as the foundational backbone for non-interactive, data-driven content, and targeted Client Components for browser-side interaction and persistent client state.

Server-rendered surfaces include the student overview dashboard, registered courses catalogue, study milestone projections, and the administrative security center. Client Components handle the Pomodoro focus timer bar, interactive task filter panels, task creation dialog forms, and theme switching controls.

This server-first composition confines client boundaries strictly to interactive UI leaves rather than making whole route segments client-rendered, significantly reducing JavaScript bundle transmission and client-side hydration work.

Hydration Optimization

StudyFlow optimizes hydration and eliminates client mismatch warnings by:

  • Confining Client Components ('use client') strictly to interactive primitive islands.
  • Serializing and passing only plain JSON primitives across the RSC-to-Client boundary (e.g. converting Prisma DateTime objects to ISO strings prior to passing props).
  • Guarding client-only state retrieval (such as next-themes and localStorage) with mount lifecycle checks to prevent React Error #418/425 mismatches.
  • Isolating volatile Pomodoro timer ticks in persistent Zustand client memory without triggering re-renders in parent server layouts.
  • Utilizing declarative loading skeletons and React <Suspense> boundaries for progressive asynchronous streaming.

Server state remains the single authoritative source of truth for enrolled courses, user security credentials, coursework deliverables, and financial ledger balances. Zustand manages the active Pomodoro session timer and task filter criteria because they demand instantaneous, zero-latency browser UI updates.

When a student submits a new task or updates deliverable progress, the client form payload is transmitted to a native Next.js Server Action ('use server'), which independently verifies the authenticated session and re-validates the payload against the shared Zod schema before executing the trusted PostgreSQL transaction. Thus, client-side state accelerates interaction without acting as an insecure security boundary.

System Architecture

1. System Overview

StudyFlow is a full-stack student productivity platform built using Next.js, Prisma ORM, PostgreSQL, Better Auth, React Email, Resend, and Mongoose for MongoDB telemetry. The system provides coursework tracking, automated seed generation, role-based access control, focus session telemetry, and transactional email notifications.

The primary backend uses PostgreSQL for relational data persistence and Prisma ORM for schema modeling, migrations, transactions, and CRUD operations. Development data is automatically generated using Faker.js through prisma/seed.ts. MongoDB captures unstructured time-series focus telemetry.

User │ ▼ Next.js Application │ ├── Authentication & Authorization │ │ │ └── Better Auth + middleware.ts (Edge JWT Guard) │ ├── UI / Server Components (RSC) │ ├── Server Actions ('use server' + Zod Validation) │ ├── Route Handlers (/api/tasks, /api/telemetry, /api/webhooks) │ ├── Prisma ORM ──────────► PostgreSQL Database │ └── Mongoose ODM ────────► MongoDB Telemetry Store

The main entity relationships are structured as follows:

User │ ├──────────────► Session │ ├──────────────► Account │ ├──────────────► Course ──────────► StudyTask ──────────► StudySession │ │ ├──────────────► AcademicGoal │ │ │ ├──────────────► Transaction │ │ │ └──────────────► AuditLog │ │ EmailDeliveryLog ◄───────────────────────┘

Main Entities

  • User: Stores registered student accounts and assigned security roles: ADMIN, MEMBER, and GUEST.
  • Session & Account: Stores authentication session tokens and credential bindings required by Better Auth.
  • Course: Represents registered academic modules (e.g. DJS23AMD302L) associated with a student workspace.
  • StudyTask: Normalized coursework deliverables with foreign keys referencing Course and User.
  • AcademicGoal: Semester milestone targets and GPA benchmarks with progress tracking percentages.
  • StudySession: Discrete Pomodoro focus intervals linked to tasks with focus quality ratings.
  • Transaction: Immutable financial ledger tracking lab allowances and research grant allocations.
  • AuditLog: Forensic records tracking critical security actions, user IDs, IP addresses, and JSON payloads.
  • EmailDeliveryLog: Transactional email dispatch records updated via Resend webhooks to log delivery and bounce events.

4. Authentication and Authorization Flow

StudyFlow uses Better Auth for session issuance and Next.js Edge Middleware (middleware.ts) for cryptographic HS256 JWT validation before requests resolve to backend route segments.

User Request │ ▼ Next.js Edge Middleware (middleware.ts) │ ▼ Session Validation (HS256 JWT Verification) │ ▼ User Role │ ┌──────────────┼──────────────┐ ▼ ▼ ▼ Guest Member Admin │ │ │ ▼ ▼ ▼ Public/ Member Admin Security limited workspace portal & audit access resources resources

The application enforces three distinct role tiers:

  • Guest: Unauthenticated or prospective user with read-only exploration access. State mutations are rejected with 403 Forbidden.
  • Member: Authenticated student with access to create/update tasks, register courses, and run Pomodoro focus sessions.
  • Admin: Authenticated faculty/administrator with exclusive access to the administrative control center, forensic audit logs, and user role management.

5. Task and Mutation Transaction Flow

When an authenticated student creates a coursework deliverable, the application performs atomic database operations through Prisma.

Student Task Submission (react-hook-form) │ ▼ Server Action (createTaskAction) │ ▼ Server-side Zod Validation (taskSchema.safeParse) │ ▼ Prisma Transaction │ ├──────────────► StudyTask (New Record) │ ├──────────────► AuditLog (Forensic Activity Record) │ └──────────────► EmailDeliveryLog (QUEUED Status) │ ▼ PostgreSQL Database

Using Prisma transactions ensures related database records are persisted atomically, preventing orphaned entries while ensuring complete auditability.

6. Transactional Email and Resend Webhook Flow

Following successful task mutation, the application prepares an alert notification using a modular React Email component and dispatches it via Resend.

Task Database Mutation │ ▼ React Email Template (TaskCreatedEmail.tsx) │ ▼ Resend API Dispatch Service (lib/email.ts) │ ▼ Student Institutional Email │ ▼ Resend Lifecycle Event (email.delivered / email.bounced) │ ▼ POST /api/webhooks/resend (Route Handler) │ ▼ EmailDeliveryLog Table (Status: DELIVERED / BOUNCED) │ ▼ PostgreSQL

The React Email component formats the HTML template with course code, priority badge, and due date. The Resend webhook handler ingests delivery events and updates the EmailDeliveryLog table, providing an authoritative database record of delivery confirmations.
